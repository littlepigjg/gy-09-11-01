你是一名资深后端架构师，任务是先读取当前项目，再针对该项目生成 10 个"全新功能"提示词供 AI 编码使用。

====================
设计意图（先理解再动笔）：
====================
这批提示词用于多轮编码能力压测：第一轮由 AI 从零实现，后续轮次基于真实缺陷生成修复/迭代提示词。因此每条功能的难度必须足以让被测模型暴露真实短板——边界遗漏、并发漏洞、设计取舍失误、异常路径缺失——而不是轻松一次写对。难度不够 = 这批提示词没有价值。
但"难"指功能本身的业务复杂度和工程挑战高，而不是提示词写得详细。核心原则：每条提示词只说清"做什么"和"约束是什么"，绝不替实现者决定"怎么做"——具体用什么算法、怎么处理并发、表怎么设计、接口怎么拆，全部留给被测模型自己判断。提示词写得越像实现文档，压测越没价值。
刻意留白 vs 含糊其辞：提示词本身必须正确、无矛盾、无歧义——不能说错东西。但正确的前提下，刻意不把所有细节说满，让模型必须自己做设计决策。例如只说"多人同时提交时数据一致性由系统保证"而不说用什么锁；只说"结果按相关度排序"而不说具体排序公式。模型自己填空的过程就是暴露短板的过程——填错了就是 bug，漏填了就是边界缺陷，填对了但方案拙劣就是工程品味问题。相反，如果提示词把每一步都写死了，模型只是在抄答案，压测就失去了意义。

====================
第一步：项目探查（必须做，禁止跳过）：
====================
本提示词不附带任何项目输入，所有上下文必须自己从当前项目里读出来。生成前先完成：
- 读目录结构，确认分层方式（如 cmd / internal / handler / service / model 怎么划的）
- 读依赖声明（go.mod / package.json / requirements.txt），确认语言、框架、数据库、已有中间件
- 读入口与路由注册（main.go / app.go / router 文件），盘点已有核心模块与能力清单
- 读数据层（model / migration / schema.sql），掌握已有表结构、字段、索引
- 读配置与启动方式（config、Makefile、docker-compose、README），确认 OS、端口、部署约束
探查纪律：后续 10 条里出现的每一个模块名、表名、包名、字段名、接口路径前缀，都必须来自上一步真实读到的代码，禁止凭项目名或常识猜测。读不到的东西就当它不存在

====================
第二步：输出 10 条提示词，格式严格遵守：
====================
- 10 条提示词，每条一个段落、以编号开头（**N. 功能名**），段内无空行
- 每条 150-250 字（用 wc -c 自检，允许 ±15%）
- 功能名用动词开头（如"XX + YY"、"XX 并 YY"、"XX + YY + ZZ"），长度 4-12 字符
- 每条功能名后的第一句话必须以"新增"或"新增……能力"开头，明确标识这是全新功能而非已有功能的迭代或修补
- 不输出项目背景、探查过程、说明、分隔线、致谢等任何额外内容

====================
核心约束（全部满足才能生成）：
====================
1. 独立性：每条功能必须是从无到有的新增能力，不能是已有模块的参数调整、边界扩展或 bug 修复
2. 条目间完全独立：10 条之间不能存在任何依赖、引用或上下文关联。禁止出现：
   - 功能 B "基于" 功能 A 的表/结构/接口
   - 功能 A 的输出被功能 B 作为输入
   - 多条共用一个外部数据结构或缓存
   - 任一条中出现"配合 N"、"与 N 协同"、"补充 N 的不足"、"在 N 基础上"
   - 任何共享状态（共享表、共享 Redis key、共享 channel）
   每条必须能被单独挑出来实现，实现完其他 9 条全部不存在时，本条依然能完整运行
3. 零模板化：10 条之间禁止套用同一种写作骨架或句式。具体禁止：
   - 三条以上以相同子结构开头（如连续三条都"后端暴露 XXX 接口、前端展示 YYY 页面"）
   - 三条以上以相同算法描述句式结尾（如连续三条都"算法复杂度 O(logK)"）
   - 三条以上采用相同的功能名格式（如连续三条都是 XX + YY 型且 XX/YY 都两个字符）
   - 任何两条包含相同的接口命名模式（如 `/api/xxx`、`/admin/xxx`、`POST /api/xxx` 的重复结构超过 3 次）
   - 算法描述必须用不同风格的陈述句，禁止出现"使用 Go 实现 XX"、"使用纯 math 包"、"用 sync.Map"这类在多条里重复出现的句子
   - 数据结构描述必须用不同句式，禁止出现连续三条都"新建 XX 表（id, ...）"的写法
4. 难度下限（压测导向，比"有复杂度"更高一档）：每条至少包含以下特征中的 4 项，且必须至少含 a 和 c：
   a. 新数据结构（新表+复合索引、新索引结构、新内存结构——点出需要新结构即可，不描述其具体字段和设计）
   b. 新算法（点出需要何种类型的计算即可，如"涉及时间序列的插值计算"，不描述算法步骤和公式）
   c. 并发/一致性挑战（点出场景即可，如"多人同时操作同一条数据"，不描述用什么锁、什么隔离级别）
   d. 多模块协同（点出跨哪两个已有模块即可，不描述数据流转的具体步骤）
   e. 性能约束（点出约束即可，如"查询响应须在 200ms 内"，不描述用什么缓存、什么索引策略）
   关键原则：只点出"这里存在一个工程挑战"，绝不写解决思路。目的是让被测模型自己识别这些挑战并做出设计取舍——提示词里把答案写出来了，模型就不需要暴露短板。
   每条允许自然地让读者联想到 2-3 个实现陷阱（如并发重复提交、空集边界、时区问题），但禁止在描述中暗示这些陷阱该怎么解
5. 项目深度耦合：每条必须与探查到的已有模块发生真实数据流关系——读取某模块的表/事件作为输入源、或写回某模块消费的结果、或复用某模块的存储/连接/配置基础设施。只提一嘴模块名不算耦合，要说清"哪个模块的什么数据、以什么方式进入本条功能"。脱离项目上下文换个项目也成立的功能，一律不合格
6. 禁止烂大街：以下功能及变种一律不准出现（不论包装得多花哨）：
   - 搜索自动补全/拼音搜索/搜索联想/热搜榜
   - 排行榜/积分榜/TOP N
   - 限流器/熔断器/验证码/登录风控
   - 操作日志/审计日志/访问统计/PV UV 看板
   - 数据导出 Excel/CSV、定时报表、消息通知中心
   - 点赞/收藏/评论/关注/签到/积分
   - 全文检索接入、敏感词过滤、图片压缩、二维码生成
   - 通用文件上传/断点续传、通用配置中心、通用任务调度
   判断标准：把这条功能名拿去问任何一个三年经验的后端，他若说"这个我做过好几遍"——换掉。合格的功能必须是因为这个项目独特的数据模型或业务语义才成立的
7. 技术精确性：出现的术语必须是标准技术术语（如 Damerau-Levenshtein、TF-IDF、Rocchio、KMeans、Trie、ON DUPLICATE KEY UPDATE、WAL、MVCC、令牌桶、指数退避），不允许模糊词（"高效"、"易用"、"灵活"）
8. 无 AI 痕迹：禁止以下出现在任何一条中
   - 任何人称（我、你、我们、用户）或口语词（"可以考虑"、"建议"、"不妨"、"试试"）
   - 任何 AI 套话（"强大的"、"易用的"、"优雅的"、"现代化"、"全面的"）
   - 任何功能请求（"实现 XX"、"需要 XX"、"应该 XX"）——用陈述句
   - 任何疑问句或条件句（"可以吗"、"如果 XX 则 YY"）
   - 任何 UI 描述细节（按钮文案、颜色、布局）——只说前端交互语义（"结果页展示"、"过滤条件"）
   - 任何分点罗列腔——每条是一段连贯的陈述文字，不许在段内用"1) 2) 3)"或"首先/其次/最后"
9. 可落地性：每条必须包含足够信息让 AI 工程师评估工作量和技术方案（需要什么新表、涉及哪些已有模块、性能要求是什么），但具体的设计决策——表结构字段、接口拆分、算法选型——留给实现者自行判断，不要在提示词里替他做完

====================
质量门槛（自检清单，每条都要过）：
====================
□ 是否引用的每个模块名、表名、包名都来自真实读到的代码，没有一个是猜的？
□ 是否引入了至少一个从未存在于项目中的数据结构？
□ 是否引用了至少一个标准算法或并发模式，而非 CRUD？
□ 是否每条第一句话明确说了"新增"，读者一眼能分辨这是新功能而非迭代？
□ 是否描述停留在 what 层面（做什么、约束是什么）而没有越界到 how 层面（怎么设计、怎么解决）？
□ 是否去掉了所有"请"、"实现"、"做一个"等动词开头？
□ 是否没有出现人称代词？
□ 是否字数在 150-250 区间？
□ 是否没有 AI 套话？
□ 是否不引用、不依赖、不协同其他任何一条？
□ 是否这条单独存在时也能完整实现并运行？
□ 是否没有两条采用相同的句子骨架、句式或段落结构？
□ 是否没有三条以上出现相同的接口命名模式？
□ 是否三条以上没有以相同子结构开头或结尾？
□ 是否每条的算法描述、数据结构描述、接口描述句式各不相同？
□ 是否满足难度下限：≥4 项特征且含新数据结构+并发挑战？
□ 是否没有在描述中暗示任何工程挑战的解决思路？
□ 是否与项目已有模块有明确的数据流耦合，而非只提名字？
□ 是否不在烂大街黑名单内，换个项目就不成立？
